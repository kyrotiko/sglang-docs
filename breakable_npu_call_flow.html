Breakable NPU Graph — 调用流程图

配图讲解 《BreakableNPUGraphBackend 设计文档》的调用流程 · 四张图：组件全景 → 录制 → 重放 → seq_lens 两条路径对比

三十秒预备知识（看图前记这三句就够）：

  • 录制（capture）：模型跑一遍，把算子序列录成"剧本"（graph）。breakable 的剧本不是一整张，是多段，段与段之间留了"断点"。
  • 重放（replay）：之后每个 decode step，段按按钮重放（快），断点函数用普通 Python 现场执行（慢一点但灵活）。
  • 断点（@eager_on_graph）：打在注意力这类"吃 host 侧 seq_lens 的算子"上——它们在图外跑，每次重放都拿到最新的 KV 长度，全图模式里那个 graph.update 重绑通道对它们就不需要了。

图 2：录制流程 — 一条 forward 怎么变成"多段 + 断点"

sequenceDiagram
    autonumber
    participant R as 捕获循环 Runner
    participant B as Backend
    participant C as Capture 拆段协调者
    participant F as 模型 forward
    participant E as 断点 eager_on_graph
    participant N as torch.npu

    R->>B: capture_session stream
    B->>B: 建池 graph_pool_handle
    R->>B: capture_one shape_key
    B->>B: warmup 2遍 + TP barrier
    B->>C: 进入捕获上下文
    C->>N: 开段1 NPUGraph
    B->>F: 运行 forward
    F->>F: 第1-2层 MLP 录进段1
    F->>E: 第3层是注意力断点
    E->>C: end_current_segment
    C->>N: 段1录制完成
    C->>C: TP barrier 对齐各卡
    E->>E: eager 跑真实注意力
    Note over E: host seq_lens 此刻当参数传入, 输出地址记为桥接 buffer
    E->>C: replay_fn 存入 break_fns 列表
    C->>N: 开段2 NPUGraph
    F->>F: 第4-N层 录进段2
    C->>N: forward 结束 段N收尾
    B->>B: 存 graphs 和 outputs 字典
  • 剪一刀 = 三步（图上 11→14 行）：结束当前段 → eager 执行断点函数 → 开新段。这就是"breakable"的全部含义。
  • 第 16 行是设计核心：断点函数执行时 host 侧 seq_lens 作为普通参数传入，它的输出张量地址被记为"桥接 buffer"——段2 录制时会焊死读这个地址。
  • 每个 shape（batch 尺寸桶）走一遍完整流程，录出一套"段列表 + 断点函数列表"，存进 _graphs 字典。
  • 每段共用同一个内存池（第 2 行），段间中间结果才能复用显存。

图 3：重放流程 — 每个 decode step 发生什么（最重要的一张）

sequenceDiagram
    autonumber
    participant R as NPUGraphRunner.execute
    participant AM as attention metadata
    participant B as Backend
    participant G as BreakableCUDAGraph
    participant S as 段 NPUGraph
    participant F as 断点函数

    R->>R: 拷 input_ids 等进静态显存格子
    R->>AM: 图外刷新 metadata (eager)
    Note over R,AM: 断点函数每次重放都现读这里, host 长度永远是新的
    R->>B: backend.replay
    Note over B: 注意: 不走 replay_with_input_update!
    B->>G: graph.replay
    loop 每个 段-断点 对
        G->>S: 段.replay 纯 kernel 一键重放
        G->>F: 断点函数现场执行
        F->>AM: 现读最新 seq_lens
        F->>F: 真实注意力 forward
        F->>F: 结果写回桥接 buffer
    end
    G-->>B: 全部段完成
    B-->>R: 返回静态输出
    R->>R: 切片到 raw_num_token 返回
  • 重放 = "按按钮（段）+ 现场干活（断点）"交替。段内是纯 NPU kernel 重放，CPU 只发一条命令；断点函数是普通 Python 调用。
  • 第 3 行是和全图模式的分水岭：先在图外 eager 刷新 attention metadata，之后断点函数（第 9 行）每次都现读——seq_lens 从此走"普通传参"路径，不再被固化进图。
  • 第 11 行"写回桥接 buffer"：断点函数的输出写进录制时记下的固定地址，下一段从那里读——数据流动闭环。
  • 对照全图模式（省略的部分）：这里没有 fence 同步、没有单 worker 线程池、没有 graph.update——那三样都是为"固化绑定"服务的，断点模式不需要。

图 4：对比 — 同一份 seq_lens，两条进入路径

flowchart TB
    subgraph FULL["全图模式 NPUCudaGraphBackend - 现状"]
        direction TB
        A1["execute 计算 seq_lens 列表 (按架构选 attr 名)"] --> A2["replay_with_input_update"]
        A2 --> A3["fence 同步: 等上一图读完 host 数组"]
        A3 --> A4["单 worker 线程池异步 graph.update 重绑"]
        A4 --> A5["整图一次 replay"]
    end
    subgraph BCGP["breakable 模式 BreakableNPUGraphBackend - 本设计"]
        direction TB
        B1["execute 图外刷新 metadata"] --> B2["backend.replay"]
        B2 --> B3["段1 replay (纯 kernel)"]
        B3 --> B4["断点函数: 现场从 metadata 读 seq_lens"]
        B4 --> B5["段2 replay ..."]
    end
  • 左边：数据被固化在图里，换新值要穿 四道专门机制（列表计算 → fence → 线程池 → update），每道都有出错面（attr 名选错、数据竞争、时序）。
  • 右边：数据走普通函数传参——刷新 metadata + 断点现读，两步，都是最普通的代码。
  • 代价：右边每步多若干次"段 launch + Python 调用"的开销（61 层模型 ≈ 61 个断点），性能净收益要真机实测（设计文档 §5.3）。
一句话总结：录制时"剪一刀、跑断点、再开新段"；重放时"段一键重放、断点现场干活"。注意力这种吃 host 数据的算子永远在断点处跑，seq_lens 每次都是新值——这就是本设计最大的结构性收益。
