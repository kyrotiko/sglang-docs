01 · WHY

重复的前缀，能不能不重算？

Prefill 的代价随上下文线性增长。RadixAttention 把已算过的 KV 留在 device 上复用；当 device 放不下时，HiCache 把它扩展到 host。

L1 命中

Device 里还在

请求前缀与 radix tree 匹配，KV 直接就在 HBM。此时只 prefill 未命中的尾部，cached_tokens 增加，不产生任何 host↔device 拷贝。

L2 命中

Device 里没了，Host 里有

树节点仍记录 host 副本。调度器把命中页从 host 回载到 device，再 prefill 剩余 token。代价是一次 H2D，而不是整段重算。

都未命中

老老实实算

L1/L2 都没有，就按正常 prefill 计算；计算出的完整页按写策略备份到 host，供后续请求复用。

02 · ARCHITECTURE

HiCache 的四个角色

不要把 HiCache 理解成“一个大 memcpy”。它由元数据（树）、记账（host pool group）、控制器（队列 + 事件）和数据面（IO backend）四层组成。

元数据

HiRadixTree

节点除了 token 序列，还记录“这段 KV 在 L1 还是 L2”。匹配结果是一个 device 前缀 + 一段 host 命中长度。

记账

HostPoolGroup

逻辑页锚点 LogicalHostPool 分配 host 槽位；SWA、压缩 KV、indexer 等 sidecar 复用同一套 host 索引，不重复分配。

调度

CacheController

维护 write / load / prefetch 队列；把一次请求拆成逐层的 H2D、整页的 D2H，并用完成事件保证层序。

数据面

IO Backend

direct / kernel / kernel_ascend 三种实现；A5 上由 AIV 的 kv_exchange 完成。

05 · MECHANISM

实现机制：从参数到 AIV 内核

HiCache 不是一个单独模块，而是“树 + 池 + 控制器 + 传输引擎”的组合。下面按一次请求的顺序拆开。

1

参数解析与默认值

--enable-hierarchical-cache、--hicache-ratio、--hicache-write-policy、--hicache-io-backend。NPU 上自动改写为 kernel_ascend，DSV4 自动选 page_first 和 acl host 内存后端。

arg_groups/fields/memory.py · hardware_backend/npu/utils.py

2

建树并挂载 host 池

UnifiedRadixCache.init_hicache 触发 hybrid stack。DSV4 走 _DeepSeekV4Strategy → build_deepseek_v4_hicache_stack，返回 HostPoolGroup 和 HybridCacheController。

mem_cache/registry.py · mem_cache/hybrid_cache/hybrid_pool_assembler.py

3

匹配：device 前缀 + host 命中长度

radix tree 返回连续前缀；host 命中按整页向下取整。sidecar（SWA / 压缩池 / indexer）按 ALL_PAGES 或 TRAILING_PAGES 校验完整性。

mem_cache/unified_radix_cache.py · managers/schedule_policy.py

4

回载：逐层 H2D + 完成事件

控制器为命中页分配 device 槽，按层提交 H2D。每层记录 LayerLoadingEvent；模型在读取某层 KV 前 wait_layer_transfer(layer_id)，保证层序。

managers/cache_controller.py · mem_cache/l2_transfer.py

5

备份与淘汰

按写策略把完整页 D2H；host 满时 LRU 回收。sidecar 不单独分配 host 槽，而是复用锚点的 host 索引，保证 KV 与 indexer 同生同死。

mem_cache/pool_host/group.py · mem_cache/memory_pool_host.py

关键数据

LayerLoadingEvent

每层一个 device event；wait(layer) 让注意力只等待自己需要的那一层，形成 H2D 与计算的重叠。

关键数据

PoolTransfer

一次 L2 传输的描述：pool 名、host/device 索引、来源池、命中策略。sidecar 通过 indices_from_pool 复用源页索引。

关键数据

Priority / Queue

写队列与读队列分离；prefill 前后台线程执行 D2H，调度线程继续推进其他请求。

06 · DEEPSEEK-V4 / V4.1

DSV4 的 KV 不是“一个池”

DeepSeek-V4 系列把 KV 拆成窗口 KV、压缩 KV、indexer、压缩状态等多个池。HiCache 必须为每一种区域建 host 池，且让它们共享同一套页生命周期。

窗口

SWA KV

mxfp8_bf16 行，每 token 544 B（512 维）。滑窗命中只需最后 N 页（TRAILING_PAGES）。

压缩

C1 / C2 KV

V4.1 压缩比 1/2。C1 每 full page 128 槽，C2 每 full page 64 槽；mxfp4 行 320 B/token。

索引

indexer K / scale

两级 indexer 的 packed fp4 K（64 B/token）+ e8m0 scale（4 B/token），决定 sparse attention 的 top-k。

状态

compressor state

V4 的 C4 持久 ring 会进 host；V4.1 的 ratio-2 状态是请求级，回载后按页边界重建，不进 HiCache。

一次命中时发生了什么

  1. 树匹配 A1–A5，host 有、device 没有 → host_hit=5 页。
  2. 锚点分配 5 个 device 槽，必要时淘汰旧页。
  3. SWA / C1 / C2 / indexer K / scale 五个池，用同一组索引逐层 H2D。
  4. 注意力读第 l 层前等待该层完成事件。
  5. 只 prefill 尾部；cached_tokens=640。
HIGH

V4.1 低压缩比路径的页几何尚未闭环（G1）

KV 的 item_bytes 用 shape[1] * element_size 计算，少乘行宽；indexer 的 host 行是 2-D，而 AIV 传输需要 5-D PA_ND 视图；ratio-1 的 indexer 还只展开 64 个槽（S=128）。详见 gap_analysis.md。

07 · ASCEND A5

Host↔Device 拷贝：AIV 分片传输

NPU 上没法直接用 cudaMemcpy。HiCache 使用 transfer_kv_*_kv_split，底层是 CANN 的 kv_exchange AIV 算子；host 内存必须先注册进 device 虚拟地址空间。

transfer_kv_all_layer_kv_split_lf_pf(
    device_indices, host_indices,
    device_k=[1, pages, slots, 1, dim],
    host_k  =[pages, 1, slots, 1, dim],
    page_size=slots, impl="auto")

transfer_kv_per_layer_kv_split_pf_lf(

限制：host 页必须是完整、连续的 slot run；payload 不做量化转换；AIV 路径不支持 NPU graph capture。

Host 内存后端

✓acl：aclrtHostRegister(ACL_HOST_REGISTER_MAPPED)，分配时逐块注册。DSV4 默认。
memfabric：Offload 预保留整个 DRAM 区间，ensure_capacity 固定总额。当前 V4.1 预留未覆盖 C1/C2（G2）。
✓page_first：host 池按 [page, layer, bytes] 组织，适合 AIV 的整页搬运。
✓逐层事件：H2D 每层完成后才能被注意力读取；避免看到半页数据。

✓ 正确的 5-D 几何（KV 池）

device: [1, npu_pages, S, 1, dim]
host  : [pages, 1, S, 1, dim]
page_size = S
index = page * S + arange(S)

C1: S=128，C2: S=64；两者 slot_page_size 都是 128，但展开槽数不同。

✗ 低压缩比 indexer 的当前代码

host row: [full_pages, byte_len] (2-D)
推 native_page_size = shape[1] = 字节数
ratio-1 只展开 K=64，而 S=128

需要用 I 个 native page 组成一个 full page 的 run；见 code_change_plan.md。

08 · KNOWN ISSUES

这条路径在 DSV4.1 上的未闭环点

教学页不掩盖问题：框架在，但 V4.1 低压缩比 host 池还需要修复与 A5 实测。以下按优先级排列。

HIGH

G1 · 低压缩比 host 池几何

KV 的 item_bytes 少乘 dim；indexer 2-D 页行与 Ascend 5-D 视图不一致；ratio-1 indexer 展开长度不足。影响：备份/回载越界或 top-k 错误。

MED

G2 · memfabric 预留漏 C1/C2

reserve_dsv4_paged_host_memory 只统计 SWA/C4/C128/C4 state；ACL 默认不受影响，memfabric 会少预留。

MED

G5 · 没有 V4.1 host 池单测与 A5 E2E

现有 NPU HiCache 用例覆盖 Qwen3 / DeepSeek-R1 / V4 C4，未覆盖 V4.1 低压缩比。必须构造“device 淘汰后再命中”的 L2 用例。

LOW

G3 · 不支持 --hicache-size

DSV4 启动期直接拒绝按 GB 定容，只能用 --hicache-ratio。首批接受该限制。

09 · VERIFY

怎么证明“真的走了 L2”

重复请求命中 L1 也会让 cached_tokens 变大，不能证明 host 路径。必须先用其它请求把 device 页挤出去，再看分层指标。

方法

先挤出 device

请求 A → 发送足够多的不同长前缀填满 device → 再请求 A。此时若仍命中，只可能来自 host。

指标

host_hit 必须是正

sglang:prefill_effective_tokens_total{mode="host_hit"} 在请求窗口内增长；cached_tokens 只说明命中，不区分层级。

正确性

greedy 逐 token 对比

同一 prompt 在“HiCache off”和“强制 L2 命中”下比较输出；不一致优先检查 indexer 与压缩状态重建。

验收清单

✓启动日志出现 SWA / C1 / C2 / indexer 各 host 池的 GB 分配
✓短 prompt（< 1 页）不缓存
✓不同前缀不误命中
✓device 淘汰后重复前缀 → host_hit > 0
✓host 池占用按容量公式增长并回落
✓压力下无泄漏、无崩溃
