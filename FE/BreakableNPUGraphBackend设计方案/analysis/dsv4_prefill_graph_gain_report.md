# DSV4 prefill 图收益分析报告（chunk 512 / 1024 / 2048）

**基线**：`sglang` 分支 `prefill_graph_ascend_ops`，包含 `393da680d6`（零 token rank 保持 SUM_LEN 的修复）。
**模型**：DeepSeek-V4-Flash-0731-w8a8，TP16 / DP16 / EP16，ascend_ops allgather MoE。
**数据**：2026-11-09 内网 bench_serving 实测，三档 chunk，每档「开图 / 不开图」各 3 次，共 18 次运行，无 profiler。
**范围**：prefill 图开关 A/B；每 rank chunk 512 / 1024 / 2048。

## 0. 结论摘要

**符号约定**：所有变化率 = 开图均值 / 不开图均值 − 1。延迟类（TTFT / P50 / P90 / P95 / P99）负数表示开图更好；吞吐列正数表示开图更好。

| chunk（每 rank） | 客户端 | 输入长度 | 输入吞吐 | 平均 TTFT | P50 | P90 | P95 | P99 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **512**（chunked-prefill-size 8192） | rate 4.2 / 并发 20 | 9216 | **+2.73%** | **−2.72%** | −3.54% | −3.36% | **−5.83%** | **−9.84%** |
| 1024（chunked-prefill-size 16384） | rate 5.0 / 并发 30 | 9216 | −0.33% | +0.80% | +0.58% | **−3.90%** | +0.06% | +0.17% |
| 2048（chunked-prefill-size 32768） | 闭环保发 / 并发 64 | 16384 | **−1.06%** | **+1.00%** | +0.55% | +0.53% | +0.78% | +2.58% |

结论：

1. **512/rank 下开图是明确收益**：吞吐 +2.7%，平均 TTFT −2.7%，P99 TTFT −9.8%；3 次开图全部优于 3 次不开图，最差的开图也比特好的不开图高 2.42%，不是噪声。实测比此前预估的 1.6% 更好。
2. **1024/rank 下平均指标中性偏负**（−0.33% 吞吐 / +0.80% 平均 TTFT），三次方向一致但幅度在 1% 内；同时 P90 改善 3.9%、run-to-run 波动减半，可表述为「均值持平、尾部更稳」。
3. **2048/rank 不是「没区别」，而是稳定地差约 1%**：吞吐 −1.06%，平均 TTFT +1.00%，且 3 次不开图全部优于 3 次开图。需要注意的是不开图组三次有 0.55% 的单调变快趋势，若两组不是交错跑，跑序/漂移可能解释其中一部分，但方向性结论不变：**此前 profiler 口径的「2048 满载 +1.6%」在干净 bench 下不成立**，符号相反。
4. **三档放在一起看，图收益随单步变短单调上升**：等效单步差值 +7.9 ms（2048）→ +1.3 ms（1024）→ −6.8 ms（512）。这与「每步固定 host/launch 开销只有在单步足够短时才进入临界路径」一致：2048 时单步约 735 ms，launch 被 device 完全掩盖，图的 replay/metadata 开销成为净成本；512 时单步约 250 ms，削减才转化为吞吐。
5. **重要混杂**：三档的 chunk 与客户端并发、输入长度是同时变化的（19.7 / 28.8 / 58.2 并发，9216 / 9216 / 16384 输入），因此不能把差异单独归因给 chunk。对外发布「小 chunk 收益」之前，必须做固定客户端参数的受控扫描（见第 6 节）。
6. 本次输出长度为 1 token、并发封顶，**吞吐与 TTFT 是同一件事**：吞吐 ≈ 并发 / 平均 TTFT（六组数据均能对上）。对外不能把 +2.7% 吞吐和 −2.7% TTFT 当成两个独立收益叠加讲。

## 3. 分析

### 3.1 三档放在一起：收益随单步变短单调上升

prefill 单步成本 = 与 token 数近似成正比的部分 + 每步固定开销（host launch、metadata 构造、AICPU dispatch、通信同步等）。固定开销不随 chunk 线性缩小，所以 chunk 越小，它在单步里的占比越高。

由总吞吐反推的**等效单步时间**（仅组内有效；跨组因客户端参数不同只能作趋势参考）：

| 组 | 每 DP 步 token 数 | 不开图 | 开图 | 差值（开图 − 不开图） |
| --- | --- | --- | --- | --- |
| 2048 | 16 × 2048 = 32768 | 734.7 ms | 742.6 ms | **+7.9 ms（+1.07%）** |
| 1024 | 16 × 1024 = 16384 | 401.2 ms | 402.5 ms | **+1.3 ms（+0.34%）** |
| 512 | 16 × 512 = 8192 | 257.1 ms | 250.2 ms | **−6.8 ms（−2.65%）** |

三档呈现单调趋势：单步越长，图越是净成本；单步越短，图越能转化为收益。与「host/device 时间比」的门槛解释一致：2048 时单步约 735 ms，launch 基本被 device 执行掩盖，图每步的 replay/metadata 固定开销（约 8 ms）成为净成本；1024 时单步约 401 ms，两者接近抵消；512 时单步约 250 ms，host 进入临界路径，净收益 6.8 ms。该解释目前是**假设**，需要 server log 上的逐 step 统计确认（见 3.2 和第 5 节）。

**与之前 profiler 结果的关系（重要）**：

- 之前从两份无 stack profile 的窗口统计得到 2048/rank 的 per-step：不开图 733.6 ms → 开图 721.7 ms（−11.9 ms，−1.62%）。
- 本次干净 bench：不开图 734.7 ms（与 profiler 的 733.6 ms 几乎一致），开图 742.6 ms（比 profiler 的 721.7 ms 慢 21 ms）。
- 也就是说，**profiler 口径只改写了图的那一侧**（或它加重了 host 侧、放大了图的收益），干净 bench 下符号相反。结论：**profiler 窗口不适合用来度量 prefill 图的收益**，对外引用 1.6% 时必须标注测量条件，且不应再作为「满载也有 1–2%」的证据。

### 3.2 为什么 1024/2048 没有收益

四个候选原因，按可能性排序：

1. **device 时间已足够长，launch 被隐藏**：图每步节省 ≈ 0，而 replay 前的输入拷贝、DP 投票（`can_run_dp_prefill_cuda_graph` min-reduce）、metadata 刷新等固定开销仍在，净值为正（2048 约 +7.9 ms/step，1024 约 +1.3 ms/step）。
2. **图覆盖率不足 100%**：如果部分 step 因桶不匹配、零 token rank 或 vote 不通过而回退 eager，收益被稀释。需要统计 server log 里 `npu graph: True` 的占比。
3. **请求数带来的 metadata 成本**：2048 组每 rank 约 3.6 个在飞请求（58.2 / 16），512 组约 1.2 个；如果 replay 前的 per-request metadata 刷新成本随请求数增长，会进一步压低高并发组的图收益。需要用日志把「每 step 请求数」与 per-step 差值做相关。
4. **桶 padding**：MAX_LEN 把各 rank 对齐到组内最大真实长度后，图还要再向上取整到 capture 桶；若某步组内最大真实长度小于桶，图会比 eager 多算行。2048 组 16k 输入、58 并发下每 rank 基本都有满 2048 token 的工作，padding 应很小，但需用 `#new-token` 分布确认。

判别方法（拿到 server log 后即可执行）：

- `scripts/profiling/compare_prefill_step_time.py --graph-log ... --eager-log ... --tokens-per-step <512|1024|2048>`：看整 chunk step 的中位数，确认逐 step 层面是否同样呈现 +7.9 / +1.3 / −6.8 ms 的趋势。
- 统计日志中 `npu graph: True` 占全部 prefill step 的比例（覆盖率）。
- `scripts/profiling/check_dp_padding_from_log.py`：看同一秒内活跃 DP rank 数与 `#new-token` 分布，排除零 token rank / 稀疏 step 的干扰。
- 对 2048 组，额外统计每 step 的请求数（`#new-seq`）与 per-step 差值的关系，验证候选原因 3。

### 3.3 尾延迟与稳定性

- **512 档**：P90 −3.4%、P95 −5.8%、P99 −9.8%；不开图 P99 三次极差 548 ms，开图 8 ms。run-to-run CV 下降 2–6 倍。
- **1024 档**：P90 −3.9%（P95/P99 持平）；P90 极差 27.5 → 12.7 ms。
- **2048 档**：没有尾部收益，P95/P99 区间重叠；开图甚至略高但无统计意义。

解释：eager 下每步的 host 侧抖动（Python 调度、metadata 构造、launch 排队）会沿请求的多个 chunk 累积成 TTFT 长尾；图把每步固化成一次 replay，抖动的来源被移除。该效应在单步短、host 参与度高的 512 档最明显；到 2048 档，device 时间占主导，图的抖动优势也被稀释。**图的收益一半在均值，一半在稳定性**——对生产环境，P99 收敛往往比平均 2–3 个点更有价值。

### 3.4 混杂因素与结论边界

三档的关键参数是同时变化的：

| 组 | chunk/rank | 输入长度 | 客户端模式 | 达成并发 | 每 rank 在飞请求（约） |
| --- | --- | --- | --- | --- | --- |
| 512 | 512 | 9216 | rate 4.2 / cap 20 | 19.7 | 1.2 |
| 1024 | 1024 | 9216 | rate 5.0 / cap 30 | 28.8 | 1.8 |
| 2048 | 2048 | 16384 | closed-loop / cap 64 | 58.2 | 3.6 |

chunk 变小、并发变小、输入变短三者同时发生。因此「图收益随 chunk 减小而上升」目前只是**观测相关性**，不能排除并发或输入长度（进而每 step 请求数、attention 长度）的贡献。要把它变成可对外的主张，必须做受控扫描：

- 固定客户端（建议 closed-loop、cap 64、16k 输入，与 2048 组一致），扫 chunk 512 / 1024 / 2048；
- 或固定 chunk = 512，扫并发 20 / 40 / 64，单独看并发的影响。

在完成之前，报告的口径应写成「在本次三组配置下，512/rank、20 并发这一档观察到 +2.7%」，而不是「小 chunk 一定 +2.7%」。

其他边界：

- 512 档的 +2.7% 是在本模型、本拓扑（TP16/DP16/EP16、ascend_ops allgather）下测得的；换模型/并行配置需要复测。
- 每组只有 3 次，且跑序未记录；512 档结论已完全分离，2048 档存在漂移嫌疑，建议补交错跑。

## 4. 建议的对外表述

1. **主打场景**：小 chunk / 低延迟 prefill（每 rank 512，即 `chunked-prefill-size 8192`）——常见于交互式低延迟、长输入且要求首 token 快、或多租户下避免单请求长时间占用 device 的部署。
   - 数据：吞吐 **+2.7%**、平均 TTFT **−2.7%**、P99 TTFT **−9.8%**，3 次开图全部优于 3 次不开图，稳定性 CV 下降 2–6 倍。
2. **中等 chunk**（每 rank 1024）：平均指标持平（±1%），P90 −3.9%，定位为「不亏、尾部更稳」。
3. **大 chunk 满载**（每 rank 2048）：**不能讲收益**。干净 A/B 是吞吐 −1.06%、平均 TTFT +1.00%，三次方向一致；可以讲「持平（1% 以内）」。此前 profiler 口径的 1.6% 与干净 bench 符号相反，不应再引用为收益。
4. 不要把它讲成无条件全局加速：收益随 host-bound 程度变化，512 档是本次唯一明确的甜点区；1024 是分界。对外发布前建议先完成 3.4 的受控扫描。

## 6. 下一步

1. **受控 chunk 扫描（最高优先级）**：固定客户端（建议 closed-loop、cap 64、16k 输入），chunk 512 / 1024 / 2048 各 3–5 次，A B A B 交错跑；这一步决定「小 chunk 收益」能否成为可对外的主张。
2. **或者固定 chunk = 512，扫并发 20 / 40 / 64**，分离并发与 chunk 的贡献。
3. 提供三档的 server log 与服务端启动命令，跑 `scripts/profiling/compare_prefill_step_time.py` 与 `scripts/profiling/check_dp_padding_from_log.py`，确认覆盖率、逐 step 差值、每 step 请求数与图开销的关系，闭环 3.2 的归因。
4. 若要把 512/rank 作为推荐配置，补一组同客户端的 512 vs 1024 vs 2048 绝对吞吐对比，量化「小 chunk 的绝对代价 + 图的补偿比例」。
5. 可选：向下扫 256/rank，验证「越小越收益」的边界；注意 256 需要桶列表包含 256（padding factor 2 不允许 256 直接跳到 1024）。

## 附录 B：复算方法

- 变化率 = 开图 3 次均值 / 不开图 3 次均值 − 1；延迟类为负数表示开图更快，吞吐为正数表示开图更快。
- 等效单步时间 = 输入吞吐 /（DP 步 token 数），其中 DP 步 token 数 = 16 × 每 rank chunk；这是在饱和稳态下的近似，包含 padding 与队列效应，仅用于组内比较。
- 吞吐与 TTFT 的关系验证见 2.4；对外的置信区间建议直接用 3 次运行的极差（本报告已给出每档的 min/max）。
- 有 server log 时，更严格的逐 step 口径（在 `BreakableNPUGraphBackend设计方案/` 下执行）：

```bash
python3 scripts/profiling/compare_prefill_step_time.py \
    --graph-log  <开图 server.log...> \
    --eager-log  <不开图 server.log...> \
    --tokens-per-step 2048   # 或 1024 / 512
```
